## Audio lifecycle assessment

- Recorder: `record` package (`AudioRecorder`) with AAC-LC, 44.1 kHz, mono, `.m4a`.
- Initial and persistent directory: the iOS app sandbox returned by `getApplicationDocumentsDirectory()`, under `recordings/`.
- Initial name: `recording_<millisecond timestamp>.m4a`; saved name is a sanitized user-entered recording name, with a timestamp added on collision. Tokens, email addresses, phone numbers, and internal user IDs are not automatically inserted, although a user can enter personal data as the display name.
- Playback: `audioplayers` `DeviceFileSource` reads the local file.
- Upload: authenticated JSON PUT sends base64 audio plus name, extension, MIME type and language; failed uploads are queued in SharedPreferences and retried. Backend restoration can write returned audio back into `Documents/recordings`.
- Retention: saved recordings are persistent user content, not temporary cache. Cancelling deletes the unsaved file. Saving copies to the final file and deletes the initial copy. User deletion deletes the local file, removes its ID/path mapping, and requests backend deletion.
- Logout/account lifecycle: client logout does not purge the persistent recordings directory or pending-upload metadata. Whether this is correct for a shared device and whether backend copies are deleted on account deletion require product/backend/privacy confirmation.
- Protection: iOS sandbox access controls apply. No app-owned code marks files globally accessible. The code does not explicitly set a stronger `NSFileProtection` class or exclude recordings from backups; those are follow-up privacy/design decisions, not silently assumed properties.
- Export/share: song export uses a user-selected Files destination; sharing uses the system share sheet. Neither needs Photo Library access. These flows do not create an app-owned temporary copy in the inspected code.
